# Change Management Product Requirements

## 1. Overview

### 1.1 Purpose
Implement a distributed change management system for Context Studio that enables collaborative editing of structure nodes and links with Git-like workflows for tracking, proposing, reviewing, and synchronizing changes.

### 1.2 Scope
- **Managed Entities**: StructureNode, StructureNodeLink (extensible to other types)
- **Core Capabilities**: Local change tracking, provisional changes, team review workflow, distributed synchronization
- **Integration**: Built on existing ChangeEvent infrastructure
- **Architecture**: SQLite for OLTP operations, DuckDB for change synchronization, S3-compatible object storage for shared data layer

## 2. Data Model Requirements

### 2.0 Architectural Separation
- **SQLite Layer**: Handles all OLTP operations, local change tracking, and vector search
- **DuckDB Layer**: Manages change synchronization, reading/writing Parquet files to S3
- **S3 Storage**: Stores changes as immutable Parquet files with partitioning for efficiency
- **No Direct Remote SQLite Access**: Prevents corruption and ensures data integrity

### 2.1 Change States
Each change must track its lifecycle state:
- `WORKING` - Uncommitted local modifications
- `STAGED` - Changes selected for proposal
- `PROPOSED` - Submitted for team review
- `APPROVED` - Accepted by team consensus
- `MERGED` - Applied to canonical state
- `REJECTED` - Declined changes (retained for history)

### 2.2 Versioning Schema
```sql
-- Entity versions table
entity_versions (
    id: UUID PRIMARY KEY,
    entity_type: ENUM('structure_node', 'structure_node_link'),
    entity_id: UUID REFERENCES (structure_nodes.id | structure_node_links.id),
    version_number: INTEGER,
    content: JSON,  -- Full entity snapshot
    state: ENUM(ChangeState),
    parent_version_id: UUID REFERENCES entity_versions.id,
    changeset_id: UUID REFERENCES changesets.id,
    author_id: STRING,
    created_at: TIMESTAMP
)

-- Changesets for grouping related changes
changesets (
    id: UUID PRIMARY KEY,
    title: STRING,
    description: TEXT,
    state: ENUM(ChangeState),
    branch_name: STRING,
    parent_changeset_id: UUID REFERENCES changesets.id,
    author_id: STRING,
    created_at: TIMESTAMP,
    merged_at: TIMESTAMP NULL
)

-- Proposals for team review
proposals (
    id: UUID PRIMARY KEY,
    changeset_id: UUID REFERENCES changesets.id,
    title: STRING,
    description: TEXT,
    status: ENUM('open', 'approved', 'rejected', 'merged'),
    required_approvals: INTEGER DEFAULT 1,
    created_by: STRING,
    created_at: TIMESTAMP,
    closed_at: TIMESTAMP NULL
)

-- Voting records
proposal_votes (
    proposal_id: UUID REFERENCES proposals.id,
    user_id: STRING,
    vote: ENUM('approve', 'reject', 'abstain'),
    comment: TEXT NULL,
    voted_at: TIMESTAMP,
    PRIMARY KEY (proposal_id, user_id)
)
```

### 2.3 Integration with Existing Models
- Extend ChangeEvent to include `changeset_id` and `state` fields
- Add `version` field to StructureNode and StructureNodeLink
- Maintain compatibility with existing event processing
- Store changes as events in SQLite locally, sync via DuckDB to S3 as Parquet

## 3. Functional Requirements

### 3.1 Local Change Management

#### 3.1.1 Working Tree Operations
- **Track Changes**: Automatically capture all modifications to StructureNode and StructureNodeLink
- **View Diff**: Show differences between working version and canonical version
- **Discard Changes**: Revert working changes to canonical state
- **Change History**: View complete history of an entity via ChangeEvent log

#### 3.1.2 Staging Operations
- **Stage Changes**: Select specific entities to include in a proposal
- **Unstage Changes**: Remove entities from staging area
- **Review Staged**: Display all staged changes with diffs
- **Create Changeset**: Bundle staged changes into a named changeset

#### 3.1.3 Version Navigation
- **Rollback**: Restore entity to any previous version using event log
- **Branch Creation**: Create isolated change branches for experimentation
- **Branch Switching**: Switch between different change branches
- **Cherry Pick**: Apply specific changes from one branch to another

### 3.2 Collaboration Workflow

#### 3.2.1 Proposal Management
- **Create Proposal**: Submit changeset for team review with title and description
- **List Proposals**: View all open/closed proposals with filters
- **View Proposal**: Display full changeset with diffs and context
- **Update Proposal**: Modify proposal description or add commits
- **Withdraw Proposal**: Cancel proposal before approval

#### 3.2.2 Review Process
- **Vote on Proposal**: Approve/reject with optional comments
- **Discussion Thread**: Comment thread per proposal
- **Approval Threshold**: Configurable number of required approvals
- **Auto-merge**: Automatically merge approved proposals
- **Conflict Detection**: Identify conflicting proposals

#### 3.2.3 Conflict Resolution
- **Automatic Resolution**: Use CRDT-based merging for non-conflicting changes
- **Manual Resolution**: UI for resolving structural conflicts
- **Merge Preview**: Show result before applying merge
- **Rebase Support**: Reapply changes on updated base

### 3.3 Synchronization

#### 3.3.1 Remote Operations
- **Push Proposals**: Upload local proposals to S3 via DuckDB as Parquet files
- **Pull Approved**: Query S3 directly with DuckDB to fetch approved changes
- **Fetch Updates**: Use DuckDB's native S3 support to query remote changes without downloading
- **Sync Status**: Display sync state and pending operations
- **CRDT Merge**: Apply CRDT operations from Parquet files to local SQLite
- **Incremental Sync**: Use partitioned Parquet structure for efficient time-range queries

#### 3.3.2 Offline Support
- **Queue Changes**: Store changes locally when offline
- **Auto-sync**: Resume synchronization when connected
- **Conflict Buffer**: Hold conflicting changes for resolution
- **Partial Sync**: Sync specific entities or changesets

## 5. Performance Requirements

### 5.1 Scalability
- Support 10,000+ entities per changeset
- Handle 100+ concurrent users without central server
- Process 1,000+ changes per second via event sourcing
- Store 1M+ version history records in partitioned Parquet
- Leverage DuckDB's columnar compression (5-10x smaller than JSON)
- Use S3 predicate pushdown for efficient querying

### 5.2 Response Times
- Local operations: < 100ms
- Staging operations: < 200ms
- Diff generation: < 500ms for 100 entities
- Sync operations: < 5s for 1,000 changes

### 5.3 Storage Optimization
- Incremental diffs for version storage
- ZSTD compression for Parquet files (automatic with DuckDB)
- Pruning of merged working versions
- Archival of old proposals
- Partitioning by date for efficient time-range queries
- Column pruning for selective field access
- Local DuckDB caching of frequently accessed remote data

### 10.2 DuckDB Views for Analytics
```sql
-- Recent changes across all users
CREATE VIEW recent_changes AS
SELECT * FROM read_parquet('s3://bucket/changes/*/*/*.parquet')
WHERE batch_timestamp > CURRENT_DATE - INTERVAL '7 days';

-- Pending proposals with vote counts
CREATE VIEW pending_proposals AS
SELECT p.*, COUNT(v.vote) as vote_count
FROM read_parquet('s3://bucket/proposals/*/metadata.parquet') p
LEFT JOIN read_parquet('s3://bucket/proposals/*/votes/*.parquet') v
  ON p.proposal_id = v.proposal_id
WHERE p.status = 'open'
GROUP BY ALL;
```

## 12. Key Design Decisions

### 12.1 Why SQLite + DuckDB Architecture
- **SQLite**: Optimal for local OLTP, reliable vector search with sqlite-vec
- **DuckDB**: Exceptional at S3 operations, Parquet handling, analytical queries
- **Separation**: Creates natural firewall between OLTP and sync layers
- **No Remote SQLite**: Avoids corruption issues with concurrent remote access

### 12.2 Why Parquet over JSON
- 5-10x compression ratio reduces storage costs
- Columnar format enables efficient analytical queries
- Native DuckDB support for reading/writing
- Partitioning enables time-range query optimization

### 12.3 Why S3-Compatible Storage
- True serverless architecture (no central database)
- Immutable change files prevent conflicts
- Works with any S3-compatible service (AWS, MinIO, etc.)
- Built-in versioning and lifecycle management

### 12.4 Why CRDT-Based Merging
- Enables truly distributed collaboration
- Automatic conflict resolution for most cases
- Maintains eventual consistency
- No central authority required for merge decisions

### 12.5 Why S3-Based Colleague Verification
- Eliminates dependency on email service configuration
- Reduces infrastructure complexity
- Works with any S3-compatible provider
- Peer verification builds trust within teams
- Out-of-band verification codes shared via existing communication channels
- No external authentication provider required
