# 11.1 LLM Analysis Flavors

Support multiple flavors of LLM analysis for each type of LLM analysis so that the definition suggestion automation can be explored and refined.

## 11.1.1 Flavor Saver Schema

Update the LLM pipelines to use prompts stored in the database instead of directly in code.

Each 'flavor' should have:

- A `pipeline` field which maps to an enumeration of the different endpoints (`suggest_term_definition`, `suggest_layer_definition`, etc)

- A `title` which is user provided

- An `llm_provider` which is the identifier of the organization which creates the LLM, as mapped from `langchain` and the `init_chat_model` method

- An `llm_model` which is the name of the llm model to be used

- An `llm_config` which is a json field containing a basic set of configuration like `temperature`, `top p`, `tok k`, `max output tokens`, etc

- A `system_prompt` containing the system prompt to be used for this flavor

- A `user_prompt` containing the user prompt to be used for this flavor

- A `version` field which is a sequential version number for this record, incremented every time the record is updated

- An `enabled` field which is boolean and denotes whether this flavor is enabled for the multi-flavor analysis

- A `last_updated` field which is the date this record was last updated

- A `date_created` field which is the date this record was created

Flavors should be stored in a table named `pipeline_flavors` in the main dataset database.

Database changes should be managed through the `migration` system, this should be migration `006_pipeline_flavors.py`

## 11.1.2 Flavor Usage

LLM pipelines should be updated to use the prompts from the flavor.

The current prompts should be moved to a "Default" flavor for each `pipeline` type, and a data populator should be created which inserts the "Default" flavors if they don't exist.

The LLM pipeline API endpoints should be updated to accept an optional parameter `flavor` and the default should be used if none is provided.

## 11.1.3 Flavor CRUD

A set of API endpoints should be created for managing and maintaining `pipeline_flavors`:

- Update an existing flavor

  - the `Default` flavor cannot be renamed but it can be set to `enabled` = false and the prompts can be edited

- Create a new flavor for a `pipeline`

  - specifying `pipeline` is required

- Deleta a flavor

  - the `Default` flavor cannot be deleted

- List the flavors

  - an optional parameter `pipeline` can be used to filter the list of flavors returned

## 11.1.4 Streaming Flavor

The LLM endpoints should be updated to stream the response back to the client using the Server Side Events pattern. Here's an example of the pattern:

```
from fastapi import FastAPI
from fastapi.responses import StreamingResponse
from langchain.callbacks.streaming_stdout import StreamingStdOutCallbackHandler
import json

class StreamingCallbackHandler(StreamingStdOutCallbackHandler):
    def __init__(self):
        self.tokens = []
    
    def on_llm_new_token(self, token: str, **kwargs):
        return token

@app.get("/stream")
async def stream_response():
    def generate():
        # Your langchain streaming setup
        for token in llm.stream("your prompt"):
            yield f"data: {json.dumps({'token': token})}\n\n"
        yield f"data: {json.dumps({'done': True})}\n\n"
    
    return StreamingResponse(
        generate(), 
        media_type="text/plain",
        headers={"Cache-Control": "no-cache"}
    )
```

Since there are multiple flavors for each `pipeline`, the client will make multiple requests simultaneously so the requests will need to be able to operate in parallel to each other.

Also, the invocation of the langchain elements should be updated to ensure the response from the upstream LLM is streamed properly.
