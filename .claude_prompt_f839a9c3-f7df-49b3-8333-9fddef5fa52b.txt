## Executive Summary

Phase 3 introduces two bounded contexts — **Knowledge Extraction** and **LLM Pipeline Management** — into the hexagonal architecture established in Phases 1–2. The extraction context is the most architecturally significant addition to date: it introduces a four-layer sequential pipeline (`kg_context` → `llm_extract` → `nlp_gap` → `reference`), three new port types (`LLMProvider`, `NLPProcessor`, `ReferenceSource`), and six external adapter integrations (OpenAI, Anthropic, spaCy, ConceptNet, DBpedia, Wikidata/schema.org). The pipeline context is simpler — CRUD for configurations plus execution tracking against `operations.db`.

The design follows the established hexagonal pattern without exception: domain entities as dataclasses, ports as `Protocol` classes, adapters implementing those protocols structurally, composition root wiring in `app.py`, and test fakes for all ports.

## System Architecture

### Bounded Context Boundaries

**Knowledge Extraction** owns the four-layer extraction pipeline and its orchestration. It depends on three driven ports (`LLMProvider`, `NLPProcessor`, `ReferenceSource`) plus a read-only dependency on `OntologyRepository` from the Ontology context (for Layer 0 KG context lookup via semantic search).

**LLM Pipeline Management** owns pipeline configuration CRUD and execution recording. It depends on `PipelineRepository` (new, against `operations.db`) and `LLMProvider` (shared with Extraction).

The cross-context dependency is intentional and narrow: Extraction reads from the ontology repository to seed KG context but never writes to it. This is a query-only coupling, consistent with how `GraphAnalysisService` already reads from `OntologyRepository`.

### Port Placement: LLMProvider

`LLMProvider` is consumed by both Extraction and Pipeline contexts. Rather than duplicating the port definition or creating a shared domain package (which would introduce coupling between bounded contexts), the port and its value types (`LLMResponse`) are defined in `domain/extraction/ports.py` — the context where the port contract is richest. The Pipeline context imports the port type for type annotations only. This follows the same pattern as `OntologyRepository` being defined in `domain/ontology/ports.py` but consumed by `GraphAnalysisService`.

If this coupling proves problematic in the future, the port can be extracted to a `domain/shared/` package, but that abstraction is not warranted now (YAGNI).

### Extraction Layer Architecture

Each extraction layer is a callable module in `domain/extraction/layers/` with a uniform interface:

```python
@dataclass
class LayerInput:
    text: str
    existing_entities: list[ExtractedEntity]  # forward-output from prior layers
    kg_context: list[dict] | None = None       # populated by Layer 0

@dataclass
class LayerOutput:
    entities: list[ExtractedEntity]
    metadata: dict | None = None
```

Each layer module exposes a single function:

| Module | Signature | Port Dependencies |
|--------|-----------|-------------------|
| `kg_context.py` | `execute(text, ontology_repo, embedding_service) -> LayerOutput` | `OntologyRepository`, `EmbeddingService` |
| `llm_extract.py` | `execute(input: LayerInput, llm: LLMProvider) -> LayerOutput` | `LLMProvider` |
| `nlp_gap.py` | `execute(input: LayerInput, nlp: NLPProcessor) -> LayerOutput` | `NLPProcessor` |
| `reference.py` | `execute(input: LayerInput, sources: list[ReferenceSource]) -> LayerOutput` | `ReferenceSource` (multiple) |

Functions — not classes — are the right abstraction here. Each layer is stateless; the only state is the forward-flowing `LayerInput`/`LayerOutput`. A class hierarchy would add ceremony without value.

### ExtractionService Orchestration

`ExtractionService` is the aggregate root of the extraction pipeline. It accepts all port dependencies via constructor injection and orchestrates the four layers:

```
ExtractionService.__init__(
    ontology_repo: OntologyRepository,
    embedding_service: EmbeddingService,
    llm: LLMProvider,
    nlp: NLPProcessor,
    reference_sources: list[ReferenceSource],
    event_publisher: EventPublisher,
)
```

The `extract(text: str) -> ExtractionResult` method:
1. Calls Layer 0 (`kg_context`) to find related ontology entities
2. Calls Layer 1 (`llm_extract`) with KG context injected into the prompt
3. Calls Layer 2 (`nlp_gap`) with accumulated entities for gap detection
4. Calls Layer 3 (`reference`) with accumulated entities for enrichment
5. Deduplicates across layers
6. Emits `ExtractionCompleted` event
7. Returns `ExtractionResult` with per-layer metrics

Each layer call is wrapped in a try/except. On failure, the layer produces an `ExtractionLayerResult` with `entities_found=0` and the pipeline continues. This is a requirement, not defensive programming — partial extraction results are more valuable than no results.

### Entity Deduplication

Deduplication logic lives in `ExtractionService` as a private method `_deduplicate(entities: list[ExtractedEntity]) -> list[ExtractedEntity]`. The priority order (L1 > L0 > L2 > L3) is encoded as a simple integer sort key derived from `source_layer`. String similarity uses a normalized Levenshtein-like comparison (case-insensitive label matching with a configurable threshold, defaulting to 0.85).

This belongs in the service, not a utility, because the priority ordering is business logic specific to the extraction pipeline.

### Reference Source Aggregation

The domain layer receives `list[ReferenceSource]` — it knows there are multiple sources but does not know which ones. Layer 3 (`reference.py`) iterates over all sources, calling `is_available()` before each, and merges results. The domain layer is source-agnostic; the composition root controls which sources are wired in.

`CachedReferenceSource` is an adapter-layer decorator (not domain). It wraps any `ReferenceSource` and interposes a SQLite cache. This is pure infrastructure — the domain never sees it.

## Scalability Design

### Pipeline Execution Model

Extraction is synchronous within a single request. For a desktop application processing one document at a time, this is appropriate. The four layers execute sequentially because each layer's input depends on the prior layer's output — there is no parallelism to exploit.

If batch extraction becomes necessary later, the composition root can wire `ExtractionService` into a background task queue. The service itself is stateless per call and safe to invoke concurrently.

### Reference Source Caching

External reference API calls are the primary latency bottleneck. `CachedReferenceSource` provides per-term caching in `reference_api_cache.db` (no migrations, droppable). Cache invalidation is by TTL or manual drop — reference data changes slowly. The local `reference.db` import provides an offline fallback, eliminating network dependency entirely for common terms.

### LLM Provider Timeout Handling

`LLMProviderRouter` must enforce per-request timeouts. The `Execution` entity captures `status="timeout"` as a distinct terminal state. Timeout duration should be configurable per-pipeline in `PipelineConfiguration.config` dict, with a sensible default (30 seconds for a desktop app).

### Operations DB Separation

Pipeline configurations and executions persist to `operations.db`, separate from `local.db`. This separation is already established in the architecture and prevents execution log volume from affecting ontology query performance.

### Configuration Convention

API keys must be read from `config.json` only. The current `Settings` model needs a new section:


### DomainEvent Placement Decision

`DomainEvent` is currently defined in `domain/ontology/events.py`. Both new contexts need to import it. Two options:

**Option A**: Import `DomainEvent` from `domain.ontology.events` in the new contexts. This creates a dependency from extraction/pipeline to ontology — semantically wrong (extraction does not depend on ontology's event model).

**Option B**: Extract `DomainEvent` to `domain/events.py` as a shared base. The ontology context imports from there instead. This is a one-line change to ontology's events.py import and breaks no existing code.

**Decision**: Option B. `DomainEvent` is a cross-cutting concern, not ontology-specific. The same applies to `EventPublisher` — it should move to `domain/ports.py` as a shared port. This refactoring is minimal (import path change only) and prevents false coupling.
