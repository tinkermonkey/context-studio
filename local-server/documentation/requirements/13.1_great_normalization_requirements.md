# 13.1 The Great Normalization

We need to normalize the database structure of `layers`, `domains`, and `terms` into a single table named `nodes`.

The table `term_relationships` should be updated to `node_links`.

Backwards compatibility should not be maintained.

## 13.1.1 Nodes Schema

The `nodes` table schema should include all of the fields in the current `layers`, `domains`, and `terms` fields and act as a superset for all 3.

- If a field is currently present in one table but not the others, it should be optional in the new table

- A new `node_type` enum field should be added and the values `layer`, `domain`, and `term` should be used for the different node types

- The current `parent_term_id` field should be replaced with a `parent_node_id` field, and the `domain_id` and `layer_id` fields should be replaced with this also

  - For existing `term` records, if there is no `parent_node_id` value, then the current `domain_id` value should be used as the `parent_node_id` value

  - For existing `domain` records the `layer_id` value should be used as the `parent_term_id` value

  - There should be validation rules that prevent a `domain` from being the child of a `term`, and prevent a `term` from being the child of a `layer`

  - The new `nodes` table will not have a `layer_id` or `domain_id` field

- The `title` uniqueness enforcement will need to be moved from the database layer to the `NodeService` layer while maintaining the current constraints:

  - For layer nodes, titles must be unique for all `layer` nodes

  - For domain nodes, titles must be unique within a layer (so, all of the nodes with the same parent layer_id)

  - For term nodes, titles must be unique within a domain

  - Consider using the Graph Service for quickly traversing the node graph to determine if there is a record with an existing title which would cause an update to violate the defined constraints

- Vector embeddings should be migrated to a virtual vector embeddings table for `nodes` which contains the `title` and `definition` embeddings for all nodes

  - The database intialization mechanism needs to be retained since that is important to the vector embedding lifecycle

  - The `title_embedding` field should be retained

  - The `definition_embedding` field should be retained

  - The new virtual table should have a `node_id` field which maps to the `id` field of the node

- Remove the `predicate_set` field and remove the concept of `predicate_set` from the application

- `node_type` and `parent_node_id` fields should be indexed

- At the database level, deletes should cascade down by `parent_node_id` references

- `primary_predicate` fields should be migrated to a field named `structural_predicate` and the values should be retained

  - Currently there are two fields which both link the predicates, `primary_predicate` and `primary_predicate_id`, which is duplicative, only `primary_predicate_id` should be retained and migrated to `structural_predicate_id`

## 13.1.2 Node Links Schema

The `term_relationships` table should be renamed `node_links` and the `source_term_id` and `target_term_id` should be renamed `source_node_id` and `target_node_id`.

- Currently, only `terms` can be linked via `term_relationships`, but in the new model any of the types of `nodes` can be linked via `node_links`

## 13.1.3 Data Migration

Existing `layers`, `domains`, and `terms` tables should be migrated to `nodes`. This should be done via the database migration mechanism as migration '006_nodes.py'.

- The total number of records should be validated after migration: the number of nodes should equal the number of layers + domains + terms

- The integrity of `parent_node_id` values should be validated after migration

## 13.1.4 Node Service

A new service layer `NodeService` should be created for centralizing business logic around nodes and node type specific constraints:

- Existing constraints enforced at the database layer specific to the node types should be moved here to node_type specific validators

- Existing business logic at the API level should be moved to the `NodeService`

- Enforce parent-child validation rules

  - Layers can have domains as children (or no parent for root layers)

  - Domains can have terms as children (must have layer parent)

  - Terms can have terms as children (must have domain parent)

## 13.1.5 Node Link Service

A new service layer `NodeLinkService` should be created for centralizing the business logic around node links:

- Nodes should only be able to be linked to nodes of the same `node_type`, so terms should only be able to be linked to terms, layers should only be able to be linked to layers, etc

## 13.1.6 API Endpoints

The existing API endpoints (`/api/layers`, `/api/domains`, `/api/terms`) should be replaced with a `/api/nodes` endpoint and business logic specific to the node types should be moved to the `NodeService`.

- Circular node references need to be checked at prevented at all create / update / move operations for all nodes. No circular references are allowed, and the Graph Service might be a good way to check this.

- A new API request signature should be created to align with the new `nodes` schema

- A new API response signature should be created to align wit the new `nodes` schema

The existing search endpoints (/api/layers/find, /api/terms/find, /api/domains/find) should be replaced with a new endpoint `/api/nodes/find` which takes an optional `node_type` parameter

## 13.1.7 Graph Events

Graph events should also be normalized to `node_events` and the `node_type` should be included in the event

Existing business logic at the event listener level should be maintained by firing the existing events based on the type of record triggering the event.


## 13.1.8 Graph Service

The Graph Service should be updated to work with the new `nodes` table:

- The `node_type` field should be used to maintain the current GraphService data structure but to populate it with the new `nodes` records

## 13.1.9 Cleanup

After the migration is complete and the testing has passed, all of the code that is no longer needed should be removed.
