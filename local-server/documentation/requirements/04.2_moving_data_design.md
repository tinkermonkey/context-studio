# Moving Data - Design Document

This document outlines the technical design for implementing the ability to move segments of the graph with their lineage, as specified in the PRD.

## Overview

The moving data feature requires implementing batch operations that maintain referential integrity while updating multiple related entities. The design focuses on three primary use cases:

1. **Domain Movement**: Moving domains between layers with all contained terms
2. **Term Movement**: Moving terms between domains with all child terms
3. **Safe Deletion**: Moving child terms away from a parent before deletion to avoid cascading deletes

## Current Data Model Analysis

Based on the existing models in `database/models.py`:

- **Layer** → **Domain** → **Term** (hierarchical relationship)
- **Term** → **Term** (parent-child relationship via `parent_term_id`)
- **Term** ↔ **Term** (relationships via `TermRelationship`)

Key constraints:
- Terms have both `domain_id` and `layer_id` (redundant for integrity)
- Unique constraint on domain title within a domain (`_domain_title_uc`)
- Cascade deletes are configured for parent-child relationships

## Design Components

### 1. New API Endpoints

#### 1.1 Move Domains
```
POST /api/domains/move
```

**Request Model:**
```python
class MoveDomainRequest(BaseModel):
    domain_ids: List[UUID]
    target_layer_id: UUID
    move_terms: bool = True  # Whether to move contained terms
```

**Response Model:**
```python
class MoveDomainResponse(BaseModel):
    moved_domains: List[DomainOut]
    moved_terms: List[TermOut]
    updated_relationships: List[TermRelationshipOut]
    warnings: List[str]  # For conflicts or issues
```

#### 1.2 Move Terms
```
POST /api/terms/move
```

**Request Model:**
```python
class MoveTermRequest(BaseModel):
    term_ids: List[UUID]
    target_domain_id: UUID
    move_children: bool = True  # Whether to move child terms
```

**Response Model:**
```python
class MoveTermResponse(BaseModel):
    moved_terms: List[TermOut]
    updated_relationships: List[TermRelationshipOut]
    warnings: List[str]
```

**Note on Safe Deletion:** 
To safely delete a term without cascading to its children, first use this endpoint to move all child terms to a different parent or domain, then use the existing `DELETE /api/terms/{id}` endpoint to remove the now-childless parent.

### 2. Core Business Logic

#### 2.1 Domain Movement Logic

```python
def move_domains_with_lineage(
    db: Session,
    domain_ids: List[str],
    target_layer_id: str,
    move_terms: bool = True
) -> MoveDomainResponse:
    """
    Move domains to a new layer with all their terms.
    
    Steps:
    1. Validate target layer exists
    2. Validate all domains exist and get current state
    3. Check for title conflicts in target layer
    4. Begin transaction
    5. Update domain layer_id
    6. If move_terms=True, update all terms' layer_id
    7. Log changes to GraphEvent
    8. Commit transaction
    """
```

#### 2.2 Term Movement Logic

```python
def move_terms_with_lineage(
    db: Session,
    term_ids: List[str],
    target_domain_id: str,
    move_children: bool = True
) -> MoveTermResponse:
    """
    Move terms to a new domain with all their children.
    
    Steps:
    1. Validate target domain exists and get its layer_id
    2. Validate all terms exist and get current state
    3. Check for title conflicts in target domain
    4. Collect all child terms recursively (if move_children=True)
    5. Begin transaction
    6. Update terms' domain_id and layer_id
    7. Update all collected child terms
    8. Log changes to GraphEvent
    9. Commit transaction
    """
```

#### 2.3 Safe Deletion Workflow

For safe deletion without cascading, use the existing APIs in sequence:

1. **Identify children**: Query `GET /api/terms?parent_term_id={parent_id}` to find all child terms
2. **Move children**: Use `POST /api/terms/move` to relocate children to a new domain or different parent
3. **Delete parent**: Use `DELETE /api/terms/{parent_id}` to safely remove the now-childless parent

This approach leverages existing functionality and maintains API consistency.

### 3. Conflict Resolution

#### 3.1 Title Conflicts
When moving entities, title conflicts may occur due to unique constraints:

**For Domains:**
- Check if domain title already exists in target layer
- Options: Rename with suffix, reject move, or allow user to specify new title

**For Terms:**
- Check if term title already exists in target domain
- Same resolution options as domains

#### 3.2 Relationship Integrity
- Term relationships should remain intact during moves
- No additional validation needed as relationships are term-to-term

### 4. Database Considerations

#### 4.1 Transaction Management
All moves must be atomic operations using database transactions:

```python
@router.post("/api/domains/move")
def move_domains(request: MoveDomainRequest, db: Session = Depends(get_db)):
    try:
        db.begin()
        result = move_domains_with_lineage(db, request.domain_ids, request.target_layer_id, request.move_terms)
        db.commit()
        db.close()  # Ensure SQLite visibility
        return result
    except Exception as e:
        db.rollback()
        raise HTTPException(status_code=500, detail=str(e))
```

#### 4.2 Event Logging
Log all moves to the `GraphEvent` table for audit trail:

```python
def log_move_events(db: Session, entity_type: str, moved_entities: List, old_data: dict, new_data: dict):
    """Log move operations to graph_events table"""
    for entity in moved_entities:
        event = models.GraphEvent(
            event_type="update",
            entity_type=entity_type,
            old_data=old_data.get(entity.id),
            new_data={
                "id": entity.id,
                "layer_id": entity.layer_id,
                "domain_id": getattr(entity, 'domain_id', None)
            },
            timestamp=datetime.datetime.now(datetime.UTC),
            processed=False
        )
        db.add(event)
```

### 5. Validation Rules

#### 5.1 Pre-move Validation
- Target layer/domain must exist
- Source entities must exist
- User must have appropriate permissions (future consideration)

#### 5.2 Safe Deletion Validation
- Parent terms must exist before attempting to move their children
- Target domain/parent for children must be valid
- Existing move validation rules apply when relocating children

#### 5.3 Conflict Handling
- Provide detailed warnings for title conflicts
- Allow batch operations to partially succeed with warnings
- Return list of successfully moved entities vs. conflicts

### 6. Performance Considerations

#### 6.1 Batch Operations
- Process moves in batches to avoid memory issues
- Use bulk update operations where possible
- Implement progress tracking for large moves

#### 6.2 Recursive Term Collection
```python
def collect_term_hierarchy(db: Session, term_ids: List[str]) -> List[str]:
    """Recursively collect all child terms"""
    all_terms = set(term_ids)
    to_process = list(term_ids)
    
    while to_process:
        current_batch = to_process
        to_process = []
        
        children = db.query(models.Term).filter(
            models.Term.parent_term_id.in_(current_batch)
        ).all()
        
        for child in children:
            if child.id not in all_terms:
                all_terms.add(child.id)
                to_process.append(child.id)
    
    return list(all_terms)
```

### 7. API Integration

#### 7.1 Error Handling
Follow existing pattern using `api_errors.py`:
- `validation_error_response()` for invalid inputs
- `conflict_error_response()` for title conflicts
- `bad_request_error_response()` for missing entities

#### 7.2 Response Format
Consistent with existing APIs:
- Return moved entities in standard format
- Include warnings array for non-blocking issues
- Provide detailed error messages for failures

## Implementation Priority

1. **Phase 1**: Basic move operations without conflict resolution
2. **Phase 2**: Add conflict detection and resolution options
3. **Phase 3**: Optimize for performance and add progress tracking
4. **Phase 4**: Add advanced features like move previews and undo operations

## Future Considerations

- **Undo Operations**: Store sufficient data in GraphEvent to enable rollbacks
- **Move Previews**: Dry-run mode to show what would be moved
- **Permissions**: Integration with future authentication system
- **Async Operations**: For very large moves, consider async processing with job queues
