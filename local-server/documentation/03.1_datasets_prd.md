# Phase 3: Datasets

This document details the requirements for maintaining multiple datasets with full lifecycle management capabilities.

## 1. Overview

A user should be able to have multiple local datasets, each with a distinct SQLite database file, and they should be able to switch between those datasets to control the active dataset. The system provides complete dataset lifecycle management including creation, import, export, and removal operations. For Phase 3, interaction is limited to one active dataset at a time.

## 2. Dataset Inventory

The server should:

- Keep track of known datasets in a JSON configuration file, capturing file paths, user-supplied titles, creation timestamps, last accessed times, schema versions, and basic metrics (layers, domains, terms, relationships counts)
- Allow users to create new datasets via API by supplying a title and filename
- Allow users to import existing dataset files via API, with automatic validation and copying to the managed datasets directory
- Allow users to list known datasets via API with full metadata and metrics
- Allow users to switch the currently active dataset via API, which triggers graceful closure of the current database connection and opening of the selected dataset
- Allow users to delete datasets via API, removing both the configuration entry and the database file
- Allow users to forget datasets via API, removing the configuration entry while preserving the database file for backup or sharing purposes
- Support configurable dataset storage directories with automatic directory creation
- Provide dataset metrics including entity counts and schema version information

## 3. Dataset Schema History

Since there will be multiple database files with potentially different schema versions, the system must handle schema evolution gracefully.

The server should use a robust migration framework following SQLite best practices to:

- Track schema version history in each database file using a dedicated schema_history table for self-contained versioning
- Implement atomic migrations with transaction safety and rollback capabilities
- Store migration checksums to ensure integrity and detect tampering
- Automatically apply pending migrations when switching to a dataset to bring it to the latest schema version
- Provide emergency skip options for migration failures while maintaining system stability
- Support migration rollback to previous schema versions when needed
- Generate new migration templates for schema evolution
- Validate migration dependencies and execution order
- Handle sqlite-vec extension loading and virtual table creation properly within the migration system

## 4. Configuration Management

The system should:

- Support multiple configuration sources with priority resolution (environment variables, configuration files, defaults)
- Provide platform-specific default dataset directories (Documents/ContextStudio/datasets)
- Allow runtime reconfiguration of dataset storage locations
- Maintain backward compatibility with existing dataset configurations
- Support both absolute and relative path specifications for dataset directories

## 5. Error Handling and Recovery

The system should:

- Validate dataset file integrity before activation
- Provide clear error messages for invalid dataset files or missing dependencies
- Handle migration failures gracefully with automatic rollback
- Support emergency dataset switching when the active dataset becomes corrupted
- Maintain system stability even when individual datasets have issues
- Preserve dataset files during configuration errors to prevent data loss
