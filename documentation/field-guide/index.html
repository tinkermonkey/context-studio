Overview · November 2026Vision & getting started

Agents propose. People decide. The graph becomes everyone's context.

Context Studio is a local-first workbench for designing and curating an ontology: the taxonomies, classes, relationship types and individuals that describe a domain. Pipelines, chat, and agents connected over MCP all suggest changes. Every suggestion waits in one review queue with its rationale and evidence. What you accept becomes structure that people browse and agents query.

The app

Schema, Data, Proposals, Claims, Sources, Pipelines and the Graph view, at localhost:3100.

The MCP server

26 tools and 2 resources at :8000/mcp, for Claude Code and client projects.

The chat assistant

The idea

An ontology that changes by proposal, not by hand edit

Most shared vocabularies live in files: a spec folder, a schema module, a wiki page. Whoever edits the file changes the model, and each agent learns the vocabulary from whatever was pasted into its prompt. Context Studio keeps the model in one place, turns every change into a reviewable proposal, and serves the result to people and agents alike. Each project's repo stays the release channel.

Get started

From a fresh checkout to a source of truth

Five steps, in the order you meet them. The first three take under an hour. After step 3 you mostly work by asking Claude, and the value compounds as reviewed decisions pile up.

1RUN

Run it locally

Clone the repo, copy local-server/config.example.json to config.json and add an Anthropic, OpenAI or OpenRouter key. Then start both servers from the repo root:

./dev.sh --migrate   # API :8000, UI :3100, waits for health
Unlocks

The app at localhost:3100, the REST API, and an MCP endpoint at :8000/mcp. All data stays in SQLite on your machine.

2SEED

Seed a schema and write its vision

On the empty Dashboard, pick Load Demo Dataset, or choose Create taxonomy and add concept schemes and classes. Open the taxonomy and fill in Summary and Vision: what the model is for and what it leaves out.

Unlocks

A browsable model with a stated purpose. The vision travels with every chat turn and MCP read, so agents work toward your intent. Schema guide

3CONNECT

Connect an agent first value

Copy the command from Configuration › Integrations, run it, then ask Claude Code about your model. Set a chat model on the General tab for the in-app assistant.

claude mcp add --transport http context-studio http://127.0.0.1:8000/mcp \
  --header "Authorization: Bearer <token>"
> Which Context Studio class fits gossip protocols? Propose one if none does.
Unlocks

Claude Code looks up your vocabulary instead of inventing it, and proposes what's missing, with links back to the app. Agents guide

4GROW

Grow it from evidence

Add a PDF, web page or pasted text under Data › Sources and extract it into a dataset, or ask an agent to. Review the proposal it produces.

> Add https://en.wikipedia.org/wiki/Raft_(algorithm) as a source and extract it into papers.
Unlocks

Individuals and relationships that cite the passage they came from, and schema gaps that show up as proposals. Sources guide

5LOOP

Run the loop with your clients compounds

Client projects send proposals over MCP and read decisions back. Review notes become triaged claims. Refinement runs sharpen definitions and connections. An approval policy applies routine, non-breaking changes by itself.

> Run definition refinement on the consensus_protocols scheme of software_architecture.
Unlocks

One reviewed, versioned source of truth for structure, plus a growing gold set of decisions to benchmark pipelines against. Proposals guide

The value

What you get for curating here

221/221

Operations accepted with no field edits when the Documentation Robotics spec was refined through Context Studio (Gate C). Both passes landed back in DR from the export with no hand-edited spec files. House now pulls its structure from Context Studio and tests its code against it.

Nothing changes unreviewed

Agent and pipeline writes are proposals. An approval policy can auto-apply routine changes; breaking changes, new taxonomies and vision edits always wait for a person.

Facts cite their source

Extracted individuals keep the page and quote they came from. The citation stays even if the source is removed later.

Everything is reversible

Every write is a change event. Revert a whole proposal in one transaction, with conflicts explained.

Decisions become data

Each accept, reject and claim verdict is stored as gold, a benchmark for the pipelines and decision models that made the suggestion.

Grounded agents

Agents read the same model you curate: semantic search, neighbors, paths, the taxonomy's vision and full bundles.

Local by default

SQLite files on your machine. The MCP server only listens on loopback and needs a bearer token.

You'll know it's working when
  • Agents answer with your class and relationship names, and propose new ones instead of inventing them.
  • Most of a proposal clears in the mechanical tier, and your time goes to the judgment calls.
  • You can answer "where did this come from?" for any fact from its page.
  • A client lands a reviewed change in its repo without hand-editing the spec.

Curate/app/schema

Schema

Design the shape of the domain: taxonomies hold concept schemes, schemes hold classes, and relationship types say how classes connect. A clear schema is what makes extraction accurate, review fast and agent answers consistent.

The modelexample
  • software_architecturetaxonomy · vision, summary, version
  • architectural_stylesconcept scheme · scope note
  • Architectural Styleclass
  • RESTsubclass · definition, attributes
  • satisfies constraint → Stateless Constraintrelationship type

From the Software Architecture demo: REST is "an architectural style for distributed hypermedia systems, defined by six constraints", and Stateless Constraint lives in the architectural_constraints scheme.

What each part carries
TaxonomySummary, vision, draft or published version, approval policy
Concept schemeScope note; becomes a layer in the graph view
ClassDefinition plus an operational definition: what to distinguish it from, evidence signals, standard reference
Relationship typePredicate, domain and range, cardinality, symmetry, edge attributes, relevance
Use cases

When you work here

New domain

Design a model from scratch

Start with a taxonomy and a one-paragraph vision, or load the Software Architecture demo to see a finished one. Sketch the schemes, then let extraction from real documents tell you which classes are missing.

Client spec

Mirror a project's spec

Import the DR spec as the dr_spec taxonomy. Check drift compares it with the spec on disk and proposes the difference.

Quality

Sharpen definitions

Operational definitions drive matching. Classes that say what they are not, and what evidence signals them, get fewer wrong extractions.

Release

Publish and share a version

Publish moves a taxonomy from draft with a commit message and diff summary. Export bundle gives clients a JSON snapshot.

Curate/app/data

Data

Individuals are the things your schema describes: a specific service, a person, a place. They live in named datasets, so several bodies of data can share one schema without mixing. Each individual shows the source passage that justified it.

One schema, many datasets?dataset= follows you across pages
Taxonomy schemaclasses + relationship types
Datasetpapers
Individualsclasses + property values
Relationshipstyped, directed edges
Provenancesource · page · quote

Example: individuals extracted from papers go in a dataset papers over the Software Architecture schema. A second dataset, say our-systems, can describe your own services with the same classes without mixing the two.

Turn documents into proposed individuals and relationships. Every candidate points back to the passage it came from, so review is a matter of reading the quote and deciding.

Grow/app/pipelines

Pipelines

The LLM pipelines that extract and refine. Configure provider, model and prompts, try a configuration on sample paragraphs, and audit every run. Results from schema-level runs arrive as proposals, so a person still decides.

Pipeline typeWhat it suggestsStart it from
individual_extractionIndividuals and relationships from a source, with passagesSources, run wizard, extract_source
schema_extractionClasses and relationship types the text needsSources, run wizard, Extraction review
schema_node_groundingLinks from classes to DBpedia and ConceptNet conceptsRun wizard, run_refinement
schema_node_definition_refinementSharper class definitionsRun wizard, run_refinement
schema_node_connection_refinementMissing or wrong relationships between classesRun wizard, run_refinement
schema_relationship_reflectionA change plan from sorting questions about relationship typesrun_refinement
notes_to_claimsAtomic claims split from review notesrun_refinement
claim_triageValidity, category, severity and fix scope for each claimrun_refinement
Decision modelsdefault: clef

Some judgments are posed as choice, score or yes/no questions answered with probabilities. Reflection and claim triage use them; their answers show up in the proposal inspector, where you can override the pick. The default clef model runs on Cloudflare Workers AI and falls back to an LLM. Configure them in config.json › decision_models.

Reference data/app/reference/sources

ConceptNet, DBpedia, Wikidata and schema.org back the grounding pipeline. A built-in proxy, reference-api-buddy, caches every response and rate-limits each upstream, so repeated runs are fast and polite. The Reference Sources page shows which upstreams are reachable.

Curate/app/proposals

Proposals

The one door. Changes from pipelines, chat, Claude Code over MCP and bundle imports all land here, with rationale, evidence and a probability. Nothing changes the ontology until it is applied, except what a taxonomy's approval policy applies by itself.

Lifecycle
Proposedchat · mcp · pipeline · bundle
Classifiededitorial · additive · breaking
Decidedaccept · edit · reject
Appliedchange events + gold
Landedclient records commit

Any applied proposal can be reverted in one transaction. Conflicts with later changes are explained before anything is undone.

MechanicalRoutine changes. Accept everything above a probability threshold with one slider.
JudgmentDecided row by row in the inspector: diff, rationale, evidence, source passage, reflection answers.
ConflictsShown side by side, including stale targets that changed since the proposal was made.

Approval policyper taxonomy

Rules on operation, kind, class and scope, plus a minimum probability, let routine changes apply as soon as they are proposed. House uses this to create activities directly while still confirming places. Three things never auto-apply: breaking changes, new taxonomies and vision edits. Every decision, manual or automatic, is stored as gold and can be exported from /api/taxonomies/{id}/gold/export.

See the structure you have curated and ask questions of it. The graph view shows layers, clusters and paths; the chat assistant answers from the workspace using the same tools agents use, and can draft proposals.

Chat assistant⌘J anywhere

An agent over the same read, propose and run tools as MCP, with the taxonomy summary in context. Ask about this on any entity page sends that page along. Proposals it drafts appear as cards you can open in review.

you   Which classes have the most individuals?
tool  search_entities · list_children
you   How does Raft relate to Paxos?
tool  find_path(Raft, Multi-Paxos)

Needs a chat model set in Configuration › General. Anthropic is used when its key works, otherwise OpenRouter.

Use cases

When you work here

Health check

Spot structural problems

Isolated classes, over-connected hubs and odd communities stand out in the clustered layout and the metrics tab.

Explain

Show how two ideas connect

Path finder or chat traces the chain of relationships between any two entities.

Analysis

Ask precise questions

SPARQL answers questions the screens don't, such as every class in one scheme that has no definition.

Drafting

Talk through a change

Describe what's wrong in chat; it reads the model and drafts a proposal for you to review.

Agents (MCP)

Connect Claude Code and client projects over MCP. Agents read the ontology and propose changes; a person reviews them in the app. One tool registry serves MCP and the in-app chat, so both see the same model.

Connect Claude Code
claude mcp add --transport http context-studio http://127.0.0.1:8000/mcp \
  --header "Authorization: Bearer <token from Configuration › Integrations>"

The README's MCP section covers setup. The token is generated on first start and saved as mcp.auth_token in config.json. Configuration › Integrations shows it and the full command. To rotate it, clear the value and restart. The MCP server only starts when the API listens on loopback.

Claude Code in your repo

While writing code or docs, the agent searches the ontology for the right class and relationship names, and proposes a new class when one is missing instead of inventing it locally.

Context Studio on its own architecture

Good to know
  • Mirrored taxonomies, such as dr_spec, accept schema proposals and refinement runs only from their own client over MCP.
  • The REST API itself has no login; origin and host checks keep other web pages out. While npm run dev runs, Vite listens on all network interfaces, so treat your local network as trusted.
  • The MCP server offers tools and resources but no prompts.
